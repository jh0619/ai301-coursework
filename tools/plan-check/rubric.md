# Rubric: is this implementation plan ready to post?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| Diagnosis follows from reproduction | Read the plan's diagnosis against the issue description and the package's Repro evidence, including commands, observed output, logs, stack traces, or failing tests. | Pass if the diagnosis identifies a cause or failure boundary that is directly supported by the reproduced behavior and does not claim more certainty than the evidence establishes. A hypothesis may pass only when it is labeled as uncertain and the plan includes a way to verify it before relying on it. Fail if the diagnosis contradicts the reproduction, explains a different failure, or presents unsupported inference as an established root cause. | required |
| Scope is bounded and specific | Read the plan's scope, files-to-change section, out-of-scope limits, and the issue's requested behavior. | Pass if the plan names the behavior and files or components it intends to change, limits the work to the issue, and states meaningful boundaries on what will not change. The named scope must be sufficient to address the issue without including unrelated cleanup or refactoring. | required |
| Approach addresses the diagnosis | Compare the plan's proposed implementation steps with its diagnosis, the reproduced failure, and the relevant code or file locations named in the package. | Pass if the proposed change acts on the diagnosed failure path, explains how the behavior will change, and identifies the important implementation locations or decision points. Fail if the approach only hides the symptom, changes an unrelated component, or depends on an unsupported assumption. | required |
| Test plan proves the fix | Compare the plan's test plan with the issue's expected behavior and the package's Repro evidence and reproduction steps. | Pass if the plan re-runs the relevant reproduction or an equivalent check through the real affected behavior, states an observable expected post-fix result, and includes a regression or control check when the change could affect existing behavior. A repeatable manual reproduction may pass; an automated test is not required unless the issue or repository requires one. Fail if the planned check can pass while skipping the original trigger, merely hides the failure, or does not distinguish the fixed behavior from the reproduced behavior. | required |
| Plan comment is accurate and compliant | Read the exact draft plan comment against the full plan, issue description, thread highlights, repo-facts contribution policy, and applicable repository instructions. | Pass if the comment accurately summarizes the diagnosis, bounded scope, approach, and verification plan; does not promise an unverified result or completion date; does not conflict with maintainer guidance; and follows every stated communication and disclosure requirement. If the repository requires AI-use disclosure, the exact draft comment must contain every required element, including the tool and extent of assistance when the policy asks for them. A mention of AI elsewhere in the issue, thread, plan, or package does not count as the contributor's disclosure. If no disclosure rule exists, absence of disclosure does not fail this check. | required |
| Risks and unknowns are explicit | Read the plan's risks, unknowns, and out-of-scope statements against the diagnosis and proposed implementation. | Pass if the plan identifies material uncertainty or regression risk that could affect the implementation or explains why no material risk remains. The plan should distinguish verified facts from assumptions and state how important unknowns will be checked. | preferred |

## Verdict rule

For a complete plan package, return `accept` (`ready`) only if every required check passes. Return `reject` (`hold`) if any required check fails or is `unclear`.

An `unclear` grade on a required check counts as failure because the package does not provide enough evidence to show that the plan is ready to post. The preferred check never changes the binary verdict, but it may be used to provide feedback or compare otherwise-ready plans.

Grade only the issue context, thread and repository facts, Repro evidence, plan, draft comment, and repository evidence that the procedure explicitly directs you to inspect. Do not fill gaps with an implementation you would personally choose, and do not assume that missing evidence exists elsewhere.
